# Longhorn direct S3 cutover

Executed with explicit user authorization on 2026-11-13. Only
`longhorn-system/longhorn-backup-s3:data.AWS_ENDPOINTS` changed, from
`https://s3.andreybondarenko.com` to
`http://s3.seaweedfs.svc.cluster.local:8333`. Internal HTTP was included in the
specific approval. Bucket `backup`, region `us-east-1`, credential references and
other Secret data were not rewritten. No workload, public route or DNS changed.

## Signed acceptance before switching

The existing native curl SigV4 client was used through Kubernetes exec. Current
Longhorn credentials passed in memory through stdin configuration, never CLI
arguments, files or logs. No temporary Pod/Secret/backup target was created.

* Signed list and GET of an existing `volume.cfg` succeeded from all three
  Longhorn managers and all three instance-managers.
* Compared the public and internal routes: root inventory plus the sampled
  volume's backup records and metadata body matched exactly.
* A separate complete metadata traversal, excluding blocks/locks directories,
  matched 72 volume configurations and 1719 backup configurations, 1791 records
  across 272 directories. No backup blocks were downloaded and no object contents
  were printed. This is not an application restore test.
* No active Longhorn backup/restore was reported before the change.

## Change and actual controller observation

Applied an atomic JSON Patch generated by `prepare_longhorn_s3.py`, guarded by
Secret name, namespace, current resourceVersion and the old endpoint value.
Only the endpoint data key was replaced. A guarded reverse patch was generated
afterward; regenerate its resourceVersion if the Secret changes before rollback.

The target reconciled at 20:14:23 UTC and again at 20:18:56 UTC, remaining
`available=true`, condition `Unavailable=False`. Hubble on the owner's node
observed forwarded TCP8333 traffic from the actual Longhorn manager directly to
the SeaweedFS Pod at 20:18:56 UTC, without issuing a manual S3 request during that
observation window. Thus acceptance includes controller traffic, not only a
separate diagnostic client's successful request.

The inventory remained 72 BackupVolumes and 1719 Backup objects. The read-only
backup verifier passed: 34/34 expected volumes have recent backups; eight backup
and five trim schedules healthy; Talos backup schedule healthy. These metadata
checks do not prove recoverability or successful future writes.

All three managers and three instance-managers stayed Ready. Their container
start times precede this maintenance window; no restart or rollout was performed.

## Remaining work and rollback

The endpoint authorization excluded creating/deleting backups and restore
volumes. A subsequent explicit request authorized one small existing-PVC backup;
that successful check is recorded below. Isolated restore and observation of the
next scheduled backup remain pending. Full cold boot and independent S3-credential
recovery are also unverified. Loki/Thanos and all other inactive startup proposals
remain unchanged.

The updated Secret is manually managed, so an unrelated Argo sync does not
restore the old endpoint. The existing BackupTarget still references the same
Secret and `s3://backup@us-east-1/`; no source manifest needs an endpoint update.
The operator runbook and dependency graph record the live route instead.

If rollback is needed, secure a quiet backup window, read the current Secret
resourceVersion, generate `prepare_longhorn_s3.py --rollback`, review the guarded
endpoint-only patch, and patch that Secret. Verify a new successful target sync
and inventory. Do not restore old credentials, restart storage components,
restore over a working volume or delete data. Restoring the public HTTPS endpoint
also restores its public-Traefik recovery dependency.
